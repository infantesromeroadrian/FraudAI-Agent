## ADR-001: LLM Provider Strategy

**Estado:** Accepted
**Fecha:** 2026-04-06

**Contexto:**
FraudAI Agent requiere un LLM con function calling robusto para orquestar 6 agentes con personalidades diferenciadas (Donna, Harvey, Louis, Jessica, Mike, Rachel). Cada agente ejecuta herramientas especializadas (tool use) y debe mantener personalidad consistente a lo largo de conversaciones multi-turn. El stack excluye GPT/Gemini por restriccion de proyecto. Hardware de desarrollo: RTX 2000 Ada 8GB VRAM, 62GB RAM.

**Opciones evaluadas:**

| Criterio | (A) Claude API para todo | (B) Modelo local para todo | (C) Hibrido Claude + local |
|---|---|---|---|
| **Function calling quality** | Excelente. Claude 3.5/4 tiene tool use nativo con structured outputs fiables | Limitado. Modelos <8B (Llama 3.1 8B Q4, Mistral 7B Q4) tienen tool use inconsistente, fallan en schemas complejos | Optimo: Claude para tool use complejo, local para routing simple |
| **Mantenimiento de personalidad** | Excelente. System prompts largos bien seguidos, sin drift notable en sesiones largas | Pobre en <8B params. Drift de personalidad tras 3-4 turns, mezcla de estilos entre agentes | Bueno: personalidades complejas en Claude, routing sin personalidad en local |
| **Latencia (P95)** | 2-5s primera respuesta (red), 1-2s streaming | 0.5-2s (inferencia local), pero 8B Q4 en 8GB VRAM satura con contextos >4K tokens | Routing <1s local + 2-5s agente via API |
| **Coste por sesion** | ~$0.15-0.40/sesion (estimado 10 turns, ~8K input + 4K output tokens por turn con Sonnet 4) | $0 (electricidad despreciable) | ~$0.10-0.30/sesion (ahorro ~30% al eliminar calls de routing de la API) |
| **Coste mensual (100 sesiones/dia)** | ~$450-1,200/mes | $0 | ~$300-900/mes |
| **Privacidad** | Datos salen a API Anthropic. Aceptable con DPA firmado | Total privacidad | Datos de routing quedan locales; datos de analisis van a API |
| **Mantenimiento** | Bajo. API gestionada | Alto. Actualizar modelos, gestionar VRAM, optimizar inference | Medio. Dos stacks que mantener |
| **Espanol legal** | Excelente en Claude Sonnet/Opus | Aceptable en Llama 3.1 8B pero con errores en terminologia juridica | Claude para legal, local para routing |

**Decision:** Opcion (C) Hibrido Claude API + modelo local.

**Configuracion concreta:**

| Componente | Modelo | Justificacion |
|---|---|---|
| **Donna (router)** | Local: Llama 3.1 8B Q4_K_M via Ollama | Tarea de clasificacion simple (5 categorias). No requiere tool use ni personalidad. Latencia <1s. 0 coste. ~5GB VRAM |
| **Harvey (fraud)** | Claude Sonnet 4 via API | Tool use complejo (5 herramientas), analisis de datos, personalidad firme. Requiere reasoning + structured output fiable |
| **Louis (compliance)** | Claude Sonnet 4 via API | Tool use + RAG legal. Citas exactas de normativa requieren precision que modelos locales <8B no alcanzan |
| **Jessica (intel)** | Claude Sonnet 4 via API | Analisis de grafos complejos, tool use con NetworkX, reasoning multi-step |
| **Mike (red team)** | Claude Sonnet 4 via API | Generacion de ataques adversariales requiere creatividad y tool use avanzado. Tarea mas compleja del sistema |
| **Rachel (data eng)** | Claude Sonnet 4 via API | Generacion de codigo Python funcional. Requiere precision en sintaxis y logica |
| **Embeddings** | Local: BGE-M3 via sentence-transformers | Modelo de embeddings multilingue, 568M params, ~2GB VRAM. Rendimiento excelente en espanol. Coexiste con Llama 8B en 8GB VRAM |
| **Reranker** | Local: BGE-reranker-v2-m3 | Cross-encoder para reranking de resultados RAG. ~600MB VRAM |

**Gestion de VRAM (8GB total):**

Los 3 modelos NO corren simultaneamente. Estrategia de carga dinamica:
- **Fase routing (Donna):** Ollama (Llama 8B Q4_K_M): ~5GB. Embeddings y reranker NO cargados.
- **Fase RAG (ingestion/retrieval):** BGE-M3 (~2GB) + BGE-reranker (~0.6GB) = ~2.6GB. Ollama descargado automaticamente por idle timeout (5min).
- **Fase agente (Claude API):** Solo embeddings para RAG contextual (~2GB). Sin competencia por VRAM.
- CUDA context overhead: ~300MB reservado permanentemente.
- Peak VRAM: ~5.3GB (Ollama activo) — margen seguro de ~2.7GB.
- Ollama `OLLAMA_KEEP_ALIVE=5m` para descargar modelo tras inactividad.

**Estrategia de fallback:**
- Si Claude API esta caido: queue de mensajes con retry exponencial (max 3 reintentos, backoff 2s/4s/8s).
- Si latencia API >10s: notificar al usuario, no degradar a modelo local (calidad insuficiente para agentes complejos).
- Donna local caido: fallback a clasificacion por keywords (regex) como ultimo recurso.

**Consecuencias:**
- Dependencia critica de Anthropic API para 5 de 6 agentes.
- Necesario DPA (Data Processing Agreement) con Anthropic para datos financieros.
- Dos runtimes de inferencia a mantener: Ollama (local) + httpx/anthropic SDK (API).
- El coste escala linealmente con el uso; necesario implementar caching de respuestas comunes.
- La VRAM queda saturada; no es posible correr modelos locales mas grandes sin descargar otros.

**Metricas de exito:**
- Donna clasifica >90% de intenciones correctamente con modelo local (benchmark de 200 queries etiquetadas).
- Latencia P95 de routing (Donna) <1.5s.
- Latencia P95 de primera respuesta de sub-agente <5s.
- Function calling accuracy >95% en Claude para tools de Harvey/Mike (benchmark de 100 llamadas).
- Coste mensual en desarrollo <$50 (uso moderado).
- Cero fallos de VRAM OOM en desarrollo normal.

## ADR-002: Vector Database

**Estado:** Accepted
**Fecha:** 2026-04-06

**Contexto:**
El sistema RAG requiere almacenar y buscar embeddings de normativa legal del BOE (estimado: ~50K-100K chunks tras procesar decenas de miles de normas). La busqueda debe ser hibrida (dense + BM25/sparse) para combinar comprension semantica con matching exacto de terminos legales (numeros de articulo, referencias cruzadas, identificadores BOE). Se necesita filtrado por metadata (fecha, materia, estado de consolidacion, tenant_id) y tenant isolation para datos de clientes.

**Opciones evaluadas:**

| Criterio | (A) ChromaDB | (B) Weaviate | (C) Qdrant | (D) pgvector | (E) FAISS |
|---|---|---|---|---|---|
| **Hybrid search nativo** | No. Solo dense. BM25 requiere implementacion externa | Si. BM25 + dense fusionados nativamente | Si desde v1.7. Sparse vectors + dense con fusion configurable | No nativo. Requiere pg_trgm o ts_vector separado | No. Solo dense (L2/IP/cosine) |
| **Filtrado por metadata** | Si. Where clauses basicas | Si. GraphQL filters avanzados | Si. Payload filters con indices, muy eficiente | Si. SQL completo | No nativo. Pre/post-filtering manual |
| **Tenant isolation** | Colecciones separadas (rudimentario) | Multi-tenancy nativo con tenant isolation real | Colecciones con payload filtering por tenant_id + colecciones separadas | Row-level security nativo (PostgreSQL) | No tiene concepto de tenants |
| **Facilidad de setup** | Trivial. `pip install chromadb`, embebido o client-server | Moderada. Docker requerido, config YAML | Facil. Docker o binario, config minimal | Facil si ya usas PostgreSQL. Extension `CREATE EXTENSION vector` | Trivial. `pip install faiss-cpu`, in-memory |
| **Escalabilidad** | Limitada. No shard nativo. OK para <1M vectors | Excelente. Sharding, replication, cluster mode | Excelente. Sharding + replication, cluster mode eficiente | Buena con PostgreSQL tuning. pgvector 0.7+ con HNSW | Excelente en read, pero single-node y sin persistencia nativa |
| **Self-hosted** | Si | Si (Docker) | Si (Docker, binario, cloud) | Si (PostgreSQL) | Si (libreria, no server) |
| **Persistencia** | Si (SQLite backend) | Si | Si (on-disk segments) | Si (PostgreSQL) | No nativa. Requiere serialize/deserialize manual |
| **RAM usage (100K vectors, 1024 dims)** | ~400MB | ~800MB-1GB | ~500MB | ~300MB (comparte con PostgreSQL) | ~400MB |
| **Ecosystem / LangChain** | Excelente integracion | Buena integracion | Buena integracion | Buena integracion | Buena integracion |

**Decision:** Opcion (C) Qdrant.

**Justificacion:**
1. **Hybrid search nativo** es requisito critico (MLR-001). Qdrant soporta sparse vectors desde v1.7, permitiendo BM25 + dense sin infraestructura adicional. ChromaDB no lo soporta y FAISS tampoco.
2. **Filtrado por metadata eficiente** con indices de payload. Esencial para filtrar por `tenant_id`, `materia`, `fecha_publicacion`, `estado_consolidacion` sin degradar latencia.
3. **Tenant isolation** via colecciones separadas (BOE compartido) + payload filtering por tenant_id (documentos de sesion). Mas robusto que ChromaDB.
4. **Rendimiento**: Qdrant esta optimizado en Rust, con uso de memoria eficiente. 100K vectors con HNSW index en <500MB RAM.
5. **Setup simple**: Docker container unico, API REST + gRPC, client Python oficial.
6. **Escalabilidad**: Cuando el MVP escale, Qdrant soporta sharding y replication sin cambiar el codigo de la aplicacion.
7. Weaviate descartado por overhead de recursos (~1GB RAM base) innecesario para MVP, y complejidad de configuracion superior a Qdrant.
8. pgvector descartado porque no necesitamos PostgreSQL para nada mas en MVP y la hybrid search no es nativa.
9. FAISS descartado por falta de persistencia nativa, metadata filtering, y tenant isolation.
10. ChromaDB descartado por falta de hybrid search nativo -- requisito no negociable para terminologia legal.

**Configuracion para MVP:**


**Estructura de colecciones:**

|---|---|---|---|


**Consecuencias:**
- Dependencia de Docker para correr Qdrant (ya necesario para sandboxing, sin coste adicional).
- El equipo debe aprender la API de Qdrant (similar a otras VDBs, curva de aprendizaje minima).
- Sparse vectors requieren generar vocabulario BM25 durante ingestion (usar `qdrant-client` con `models.SparseVector`).
- Migracion desde Qdrant a otra VDB en produccion es factible pero requiere re-indexacion.

**Metricas de exito:**
- Hybrid search retrieval accuracy >85% en benchmark de 100 preguntas legales (RAGAS Context Precision + Recall).
- Latencia de busqueda P95 <200ms para 100K vectors con filtros de metadata.
- Zero cross-tenant data leakage en tests de aislamiento.
- Ingestion completa del corpus BOE inicial en <2 horas.

## ADR-003: LangGraph Architecture Design

**Estado:** Accepted
**Fecha:** 2026-04-06

**Contexto:**
FraudAI Agent orquesta 1 router (Donna) + 5 sub-agentes especializados con herramientas propias. El flujo requiere: clasificacion de intenciones, routing dinamico, ejecucion de herramientas por agente, escalacion entre agentes cuando un caso cruza dominios (ej: fraude + compliance), y contexto compartido de sesion. LangGraph proporciona grafos de estado con checkpointing nativo para persistencia de conversacion.

**Decision de API: StateGraph (Graph API)**

Se usa la **Graph API con StateGraph** en lugar de la Functional API por las siguientes razones:
1. El flujo es un grafo explicito con nodos (agentes) y edges (routing) bien definidos.
2. StateGraph permite checkpointing nativo por thread, esencial para sesiones multi-turn.
3. La Functional API es mejor para pipelines lineales; nuestro caso tiene branching condicional y ciclos.
4. Human-in-the-loop (confirmacion antes de red teaming) se implementa nativamente con `interrupt()`.

**State Schema:**

```python
from typing import Annotated, Literal, Any
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages
from langchain_core.messages import BaseMessage


class AgentState(TypedDict):
    """Estado global del grafo. Compartido entre todos los nodos."""
    # Historial de mensajes (acumulativo via reducer add_messages)
    messages: Annotated[list[BaseMessage], add_messages]

    # Agente actualmente activo
    current_agent: Literal[
        "donna", "harvey", "louis", "jessica", "mike", "rachel"
    ] | None

    # Agente previo (para escalacion y retorno)
    previous_agent: str | None

    # Metadata de sesion
    session_id: str
    tenant_id: str
    user_tier: Literal["free", "pro", "enterprise"]

    # Contexto compartido entre agentes (documentos subidos, resultados previos)
    shared_context: dict[str, Any]

    # Documentos subidos por el usuario (referencias a archivos indexados)
    uploaded_documents: list[dict[str, str]]

    # Resultados de herramientas del agente actual
    tool_results: list[dict[str, Any]]

    # Flag de escalacion: el agente actual solicita colaboracion
    escalation_request: dict[str, Any] | None

    # Flag para confirmacion humana (Mike red teaming)
    needs_human_confirmation: bool

    # Idioma detectado de la sesion
    language: Literal["es", "en"]

    # Contador de turns para control de costes
    turn_count: int
```

**Diseno del grafo:**

```
                    +-----------+
                    |   START   |
                    +-----+-----+
                          |
                          v
                   +------+------+
                   |    DONNA    |  <-- Modelo local (Llama 8B)
                   |   (router)  |  <-- Clasifica intencion
                   +------+------+
                          |
            +-------------+-------------+
            |       |       |      |    |
            v       v       v      v    v
        +------+ +-----+ +----+ +----+ +------+
        |HARVEY| |LOUIS| |JESS| |MIKE| |RACHEL|
        +--+---+ +--+--+ +-+--+ +-+--+ +--+---+
           |        |       |      |       |
           |  (tool calls + LLM reasoning) |
           |        |       |      |       |
           +--------+-------+------+-------+
                          |
                          v
                   +------+------+

                   +------+------+

           +-----------+    +------+------+
           |    END    |    |    DONNA    |  <-- Si el usuario
           +-----------+    +-------------+     sigue conversando
```

**Pseudo-codigo del grafo:**

```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.postgres import PostgresSaver  # o MemorySaver para dev
from langgraph.types import interrupt, Command


def build_fraud_ai_graph() -> StateGraph:
    """Construye el grafo principal de FraudAI Agent."""

    graph = StateGraph(AgentState)

    # === NODOS ===

    graph.add_node("donna", donna_router_node)
    graph.add_node("harvey", harvey_agent_node)
    graph.add_node("louis", louis_agent_node)
    graph.add_node("jessica", jessica_agent_node)
    graph.add_node("mike", mike_agent_node)
    graph.add_node("rachel", rachel_agent_node)
    graph.add_node("human_confirmation", human_confirmation_node)
    graph.add_node("responder", responder_node)

    # === EDGES ===

    # START -> Donna siempre
    graph.add_edge(START, "donna")

    # Donna -> agente via routing condicional
    graph.add_conditional_edges(
        "donna",
        route_from_donna,
        {
            "harvey": "harvey",
            "louis": "louis",
            "jessica": "jessica",
            "mike": "human_confirmation",  # Mike requiere confirmacion
            "rachel": "rachel",
            "clarify": "responder",  # Donna pide aclaracion al usuario
        },
    )

    # Cada agente -> responder O escalacion a otro agente
    for agent in ["harvey", "louis", "jessica", "mike", "rachel"]:
        graph.add_conditional_edges(
            agent,
            route_after_agent,
            {
                "respond": "responder",
                "escalate": "donna",  # Vuelve a Donna para re-routing
            },
        )

    # Human confirmation -> Mike (si aprueba) o responder (si rechaza)
    graph.add_conditional_edges(
        "human_confirmation",
        route_after_confirmation,
        {
            "approved": "mike",
            "rejected": "responder",
        },
    )

    # Responder -> END
    graph.add_edge("responder", END)

    return graph.compile(
        checkpointer=checkpointer,  # Persistencia de sesion
        interrupt_before=["human_confirmation"],  # Pausa antes de confirmacion
    )


# === FUNCIONES DE ROUTING ===

def route_from_donna(state: AgentState) -> str:
    """Donna clasifica la intencion y decide a que agente derivar."""
    return state["current_agent"] or "clarify"


def route_after_agent(state: AgentState) -> str:
    """Decide si el agente responde o escala a otro."""
    if state.get("escalation_request"):
        return "escalate"
    return "respond"


def route_after_confirmation(state: AgentState) -> str:
    """Comprueba si el usuario aprobo la accion de Mike."""
    # interrupt() pausa el grafo y espera input del usuario
    # El resultado se inyecta via Command(resume=...)
    if state.get("needs_human_confirmation"):
        return "rejected"
    return "approved"


# === NODOS DE AGENTES ===

async def donna_router_node(state: AgentState) -> dict:
    """
    Nodo Donna: clasifica intencion con modelo local.
    Actualiza current_agent segun clasificacion.
    """
    # Usa Ollama (Llama 8B) para clasificar
    user_message = state["messages"][-1].content
    classification = await classify_intent_local(user_message)

    return {
        "current_agent": classification.agent,
        "previous_agent": state.get("current_agent"),
        "language": classification.language,
        "turn_count": state.get("turn_count", 0) + 1,
    }


async def harvey_agent_node(state: AgentState) -> dict:
    """
    Nodo Harvey: analisis de fraude transaccional.
    Usa Claude Sonnet via API con tool use.
    """
    # Claude API con tools: analyze_transactions, detect_patterns,
    # generate_rules, risk_scoring, search_boe
    response = await invoke_claude_agent(
        agent_name="harvey",
        system_prompt=HARVEY_SYSTEM_PROMPT,
        tools=HARVEY_TOOLS,
        state=state,
    )

    return {
        "messages": [response.message],
        "tool_results": response.tool_results,
        "shared_context": {
            **state.get("shared_context", {}),
            "last_analysis": response.analysis_summary,
        },
        "escalation_request": response.escalation,
    }


async def human_confirmation_node(state: AgentState) -> dict:
    """
    Nodo de confirmacion humana para Mike (red teaming).
    Usa interrupt() de LangGraph para pausar y esperar input.
    """
    # Describe la accion que Mike quiere ejecutar
    action_description = format_mike_action(state)

    # interrupt() pausa el grafo -- el usuario debe aprobar via Command(resume=...)
    user_decision = interrupt(
        {
            "action": "confirm_red_teaming",
            "description": action_description,
            "warning": "Esta accion ejecutara herramientas ofensivas contra el target especificado.",
        }
    )

    return {
        "needs_human_confirmation": not user_decision.get("approved", False),
    }
```

**Checkpointing Strategy:**

| Entorno | Checkpointer | Justificacion |
|---|---|---|
| Desarrollo / MVP | `MemorySaver` | In-memory, sin dependencias. Suficiente para MVP single-instance. Sesiones se pierden al reiniciar |
| Testing | `MemorySaver` | Tests rapidos sin I/O |
| Produccion (post-MVP) | `PostgresSaver` | Persistencia real, permite resumir sesiones tras desconexion. Requiere PostgreSQL en docker-compose |

**Nota:** PostgreSQL NO es dependencia del MVP. Se usa `MemorySaver` hasta que la persistencia de sesiones sea requisito de negocio. Esto elimina una dependencia de infraestructura innecesaria para el MVP.

Configuracion del checkpointer:
- `thread_id`: `session_{tenant_id}_{session_uuid}` -- identifica sesion unica.
- Cada turn del usuario genera un checkpoint. El usuario puede "rebobinar" a un turn anterior.
- Checkpoints expiran tras 24h de inactividad (limpieza por cron).
- Datos sensibles (datasets del cliente) NO se almacenan en checkpoints -- solo referencias a archivos temporales.

**Memoria por agente:**

Los agentes no tienen memoria independiente. La memoria es el `AgentState` compartido:
- `messages`: historial completo de la conversacion (todos los agentes ven todo).
- `shared_context`: diccionario acumulativo donde cada agente deposita resultados relevantes.
- `uploaded_documents`: lista de documentos de la sesion, accesibles por cualquier agente.

Esto simplifica la implementacion y evita inconsistencias entre memorias separadas. El contexto se pasa al LLM via mensajes (el system prompt de cada agente filtra lo relevante).

**Flujo de escalacion (ejemplo: Harvey detecta posible blanqueo -> escala a Louis):**

```python
# Harvey detecta patron de blanqueo en su analisis
async def harvey_agent_node(state: AgentState) -> dict:
    response = await invoke_claude_agent(...)

    if response.detected_money_laundering:
        return {
            "messages": [response.message],
            "escalation_request": {
                "from": "harvey",
                "to": "louis",
                "reason": "Patron de blanqueo detectado. Requiere analisis de compliance.",
                "context": response.analysis_summary,
            },
        }

    return {"messages": [response.message], "escalation_request": None}


# route_after_agent detecta escalation_request y envia a Donna
# Donna re-routea a Louis con el contexto de Harvey en shared_context
```

**Consecuencias:**
- El estado global crece con cada turn (mensajes acumulativos). Necesario implementar truncado de historial (ventana deslizante de N mensajes + resumen) para controlar tokens.
- El interrupt() de LangGraph para human-in-the-loop requiere que el frontend gestione el estado "waiting for confirmation" correctamente.
- La escalacion pasa siempre por Donna (re-routing) en lugar de conexion directa entre agentes. Esto es intencional: Donna registra todas las transiciones y puede rechazar escalaciones invalidas.
- Los checkpoints de PostgresSaver necesitan un PostgreSQL en produccion (Docker Compose lo incluira).

**Metricas de exito:**
- Donna routea correctamente >90% de intenciones en primera derivacion (benchmark 200 queries).
- Escalacion entre agentes preserva 100% del contexto relevante (tests de integracion).
- Human-in-the-loop para Mike funciona sin errores en 100% de los casos.
- Checkpointing permite resumir sesion tras desconexion sin perdida de estado.
- Latencia de routing (Donna) + transfer a sub-agente <3s P95.

## ADR-004: Sandboxing Strategy

**Estado:** Accepted — parcialmente sustituido por ADR-007 (modelo de ejecucion, red y limites; ver ADR-007)
**Fecha:** 2026-04-06

**Contexto:**
Tres agentes ejecutan codigo o acciones potencialmente peligrosas:
- **Rachel** genera y ejecuta codigo Python (ETL, feature engineering).
- **Mike** lanza ataques adversariales, prompt injection, y herramientas ofensivas.
- **Harvey** ejecuta analisis estadistico y modelos ML sobre datasets del cliente.

Requisitos de seguridad (SEC-001):
- Aislamiento total del filesystem del host.
- Sin acceso a red externa excepto APIs autorizadas.
- Timeout 10 min, 4GB RAM, 2 CPU cores por ejecucion (nota: el BRD menciona 8GB en SR-008 y 4GB en SEC-001; usamos 4GB como default con opcion de escalar a 8GB para datasets grandes).
- Sin persistencia entre ejecuciones.

Hardware de desarrollo: ThinkPad con 62GB RAM, RTX 2000 Ada.

**Opciones evaluadas:**

| Criterio | (A) Docker efimero | (B) gVisor + Docker | (C) Firecracker microVMs | (D) nsjail |
|---|---|---|---|---|
| **Seguridad** | Buena. Namespaces + cgroups + seccomp. Kernel compartido (riesgo teorico de escape) | Excelente. Kernel de usuario (Sentry) intercepta syscalls. Superficie de ataque minima | Excelente. microVM real con kernel propio. Aislamiento de nivel hardware | Buena. Sandboxing a nivel de proceso con namespaces + seccomp + chroot |
| **Latencia de startup** | ~0.5-2s (con imagen pre-pulled) | ~1-3s (overhead de Sentry + Docker) | ~125ms (boot de microVM optimizado) | ~50ms (fork de proceso) |
| **Overhead de recursos** | Bajo. Comparte kernel, ~50MB base por container | Medio. +20-30% overhead de CPU por interceptacion de syscalls | Bajo por VM pero requiere KVM. ~30MB por microVM | Muy bajo. ~5MB por proceso sandboxeado |
| **Complejidad de implementacion** | Baja. Docker SDK para Python, dockerfiles sencillos | Media. Requiere instalar gVisor, configurar runtime, testing | Alta. Requiere KVM habilitado, configuracion de red compleja, sin Docker Compose nativo | Media. Build from source, configuracion de policies, menos documentacion |
| **Compatibilidad con Docker Compose** | Nativa | Si (runtime: runsc) | No. Requiere orquestador propio (Flintlock o custom) | No. Proceso independiente |
| **Soporte de GPU** | Si (nvidia-container-toolkit) | Limitado. gVisor no soporta GPU passthrough de forma estable | No soporta GPU | No soporta GPU |
| **Network isolation** | Si. Docker networks + iptables | Si (heredado de Docker) | Si (tap devices dedicados) | Si (network namespaces) |
| **Madurez / Ecosystem** | Excelente. Standard de la industria | Buena. Usado en GKE, pero nicho fuera de Google | Buena. Usado en AWS Lambda, pero complejo self-hosted | Media. Usado en Google (internamente), comunidad pequena |

**Decision:** Opcion (A) Docker containers efimeros, con perfil de seguridad reforzado.

**Justificacion:**
1. **Complejidad vs seguridad**: Para un MVP, Docker con seccomp + network isolation + resource limits cubre el modelo de amenazas. Los agentes ejecutan codigo Python controlado, no binarios arbitrarios de atacantes externos.
2. **GPU**: Harvey puede necesitar GPU para modelos ML (Isolation Forest, autoencoders). Solo Docker soporta GPU passthrough de forma estable. gVisor y Firecracker no.
3. **Docker Compose**: El proyecto ya usa Docker Compose (ADR-006). Containers efimeros se integran nativamente.
4. **Latencia**: 0.5-2s de startup es aceptable (el SLA de primera respuesta es <5s, y el container se crea mientras el agente procesa).
5. **62GB RAM**: Sobra RAM para multiples containers simultaneos (4GB x 10 containers = 40GB, queda 22GB para el host).
6. Firecracker descartado por complejidad de setup y falta de soporte GPU.
7. gVisor descartado por overhead de CPU y soporte GPU inestable.
8. nsjail descartado por falta de integracion con Docker Compose y comunidad mas pequena.

**Mejora futura**: Si el threat model escala (clientes ejecutan codigo arbitrario, no solo generado por agentes), migrar a gVisor runtime (`runsc`) es un cambio de una linea en Docker Compose (`runtime: runsc`).

```python
    input_files: list[str] | None = None,

    config = {**SANDBOX_CONFIG}

        # Red restringida: solo IPs autorizadas (API BOE, etc.)
        config["network_mode"] = "fraudai-sandbox-net"

    if input_files:

            mounts.append(

                    target=f"/data/{Path(f).name}",
                    source=f,
                    type="bind",
                    read_only=True,
                )
            )

    container = client.containers.run(
        image=config.pop("base_image"),
        command=["python", "-c", code],
        detach=True,
        mounts=mounts,
        **config,
    )

    try:

        logs = container.logs(stdout=True, stderr=True)
        return SandboxResult(
            exit_code=result["StatusCode"],
            stdout=logs.decode("utf-8"),
            timeout=False,
        )
    except Exception:
        container.kill()
        return SandboxResult(exit_code=-1, stdout="", timeout=True)
```

## ADR-005: BOE Ingestion Pipeline Design

**Estado:** Accepted
**Fecha:** 2026-04-06

**Contexto:**
El sistema RAG necesita un corpus actualizado de normativa legal espanola del BOE, especializada en fraude bancario, AML, KYC, PSD2, proteccion de datos, y regulacion de IA. El BOE ofrece APIs publicas verificadas para legislacion consolidada, sumarios, y datos auxiliares. El corpus estimado es de decenas de miles de normas, con actualizaciones semanales. El chunking debe ser semantico (por articulo/seccion legal) para mantener coherencia en retrieval.

### Fase 4: Chunking semantico por articulo

**Estrategia de chunking:**

El chunking legal NO puede ser por tamano fijo (512 tokens). Un articulo es la unidad minima de significado legal. La estrategia es:

1. **Unidad primaria**: Articulo individual. La mayoria de articulos del BOE caben en 500-2000 tokens.
2. **Articulos largos (>2000 tokens)**: Dividir por apartados numerados (1., 2., a), b)) preservando el encabezado del articulo como contexto.
3. **Articulos cortos (<100 tokens)**: Agrupar con el siguiente si estan relacionados (misma seccion).
4. **Contexto jerarquico**: Cada chunk incluye como prefijo la cadena `Ley > Titulo > Capitulo > Seccion > Articulo` para que el embedding capture el contexto legal completo.

```python
# ingestion/chunker.py
from dataclasses import dataclass

MAX_CHUNK_TOKENS = 2000
MIN_CHUNK_TOKENS = 100
OVERLAP_CONTEXT_TOKENS = 200  # Contexto jerarquico como prefijo


@dataclass
class LegalChunk:
    chunk_id: str  # "{boe_id}_art_{num}" o "{boe_id}_art_{num}_apt_{sub}"
    text: str
    context_prefix: str  # "Ley 10/2010 > Titulo II > Capitulo III > Art. 18"
    full_text: str  # context_prefix + text (lo que se embede)
    metadata: dict  # boe_id, articulo, seccion, materia, fechas, etc.


def chunk_legal_document(doc: CleanDocument) -> list[LegalChunk]:
    """Chunking semantico de documento legal."""
    chunks = []

    for article in doc.structure.articles:
        context = build_context_prefix(doc, article)
        full_text = f"{context}\n\n{article.text}"
        token_count = count_tokens(full_text)

        if token_count <= MAX_CHUNK_TOKENS:
            # Articulo cabe en un chunk
            chunks.append(
                LegalChunk(
                    chunk_id=f"{doc.boe_id}_art_{article.number}",
                    text=article.text,
                    context_prefix=context,
                    full_text=full_text,
                    metadata=build_metadata(doc, article),
                )
            )
        else:
            # Articulo demasiado largo: dividir por apartados
            sub_chunks = split_by_subsections(article, context, doc)
            chunks.extend(sub_chunks)

    # Incluir preambulo y disposiciones como chunks separados
    if doc.structure.preamble:
        chunks.extend(chunk_preamble(doc))
    if doc.structure.dispositions:
        chunks.extend(chunk_dispositions(doc))

    return chunks


def build_context_prefix(doc: CleanDocument, article) -> str:
    """Construye prefijo jerarquico para contexto de embedding."""
    parts = [doc.metadata.get("titulo", "")]
    if article.titulo:
        parts.append(f"Titulo {article.titulo}")
    if article.capitulo:
        parts.append(f"Capitulo {article.capitulo}")
    if article.seccion:
        parts.append(f"Seccion {article.seccion}")
    parts.append(f"Articulo {article.number}")
    return " > ".join(parts)
```

```python
from sentence_transformers import SentenceTransformer
from qdrant_client.models import SparseVector
import numpy as np

# BGE-M3: modelo multilingue, 1024 dimensiones, excelente en espanol
DENSE_MODEL = SentenceTransformer("BAAI/bge-m3")

# Para sparse vectors (BM25-like), usamos la funcionalidad nativa de BGE-M3
# que genera tanto dense como sparse embeddings


def generate_embeddings(chunks: list[LegalChunk]) -> list[ChunkWithEmbeddings]:
    """Genera embeddings dense y sparse para cada chunk."""
    results = []

    # Batch processing para eficiencia (BGE-M3 soporta batches)
    texts = [chunk.full_text for chunk in chunks]

    dense_embeddings = DENSE_MODEL.encode(
        texts,
        normalize_embeddings=True,
        batch_size=32,
        show_progress_bar=True,

    # Sparse embeddings (BGE-M3 lexical weights)
    # BGE-M3 puede generar sparse representations nativamente
    sparse_embeddings = generate_sparse_vectors(texts)

                chunk=chunk,
                dense_vector=dense.tolist(),
                sparse_vector=sparse,
            )
```

```python
                    "sparse": chunk.sparse_vector,

                payload=payload,
```

```python
        results.append({"query": vq["query"], "hit": hit})

    accuracy = sum(r["hit"] for r in results) / len(results)
    return ValidationReport(accuracy=accuracy, details=results)
```

### Estrategia de actualizacion: Incremental

| Estrategia | Cuando |
|---|---|
| **Full re-index** | Primera ingestion, cambio de modelo de embeddings, corrupcion detectada |
| **Incremental** | Ejecucion semanal normal. Solo descarga normas modificadas desde ultima ingestion |

La actualizacion incremental funciona asi:
1. Consulta sumarios de la ultima semana para nuevas disposiciones.
2. Consulta API de legislacion consolidada filtrando por `fecha_ultima_modificacion > ultima_ingestion`.
3. Para normas modificadas: re-descarga, re-chunka, re-embede, y upsert (overwrite por `chunk_id + version`).
4. Normas derogadas: actualiza metadata `estado_consolidacion = "derogado"` pero no elimina chunks (historico).
5. Genera nueva version del corpus: `2026-W{semana}`.

**Consecuencias:**
- El rate limiting conservador (0.5s entre requests) hace que la primera ingestion completa pueda tardar varias horas. Aceptable porque es one-time.
- APScheduler corre in-process con FastAPI; si el servidor se reinicia durante ingestion, el job se pierde. Mitigado con `misfire_grace_time` y flag de estado en DB.
- El chunking semantico por articulo requiere parsing robusto de la estructura legal del BOE, que varia entre normas. Necesita tests extensivos con normas reales.
- BGE-M3 genera embeddings de 1024 dims; mas grandes que los 384 de modelos ligeros. Aumenta almacenamiento pero mejora calidad de retrieval en espanol legal.

**Metricas de exito:**
- Primera ingestion completa en <4 horas.
- Ingestion incremental semanal en <30 minutos.
- Validacion post-ingestion (spot check 10 queries): >90% hits en top-5.
- Zero chunks con texto vacio o corrupto (data quality check).
- Versionado de corpus funcional: rollback a version anterior en <5 minutos (cambio de filtro en Qdrant por `version_corpus`).

## ADR-006: Deployment & Infrastructure

**Estado:** Accepted
**Fecha:** 2026-04-06

**Contexto:**
FraudAI Agent necesita un entorno de desarrollo local funcional para el MVP, que sea reproducible y que prepare el camino para produccion. El hardware de desarrollo es un ThinkPad con RTX 2000 Ada 8GB VRAM y 62GB RAM. El sistema tiene multiples componentes: FastAPI, LangGraph, Qdrant, Ollama, containers de sandbox, y opcionalmente PostgreSQL para checkpoints.

**Opciones evaluadas:**

| Criterio | (A) Full local dev (sin Docker) | (B) Docker Compose local | (C) Docker Compose + cloud para LLM API |
|---|---|---|---|
| **Simplicidad** | Alta para empezar, baja para replicar | Media para empezar, alta para replicar | Media para empezar, alta para replicar |
| **Reproducibilidad** | Baja. "Works on my machine" | Alta. `docker compose up` y listo | Alta. Misma que (B) + API keys configuradas |
| **Coste** | $0 (todo local) | $0 (todo local) | ~$10-50/mes en desarrollo (Claude API) |
| **Portabilidad prod** | Requiere Dockerizar todo despues | Ya Dockerizado, deploy a cualquier cloud | Listo para deploy con cambio minimo de config |
| **Sandboxing** | No funciona sin Docker | Funciona nativamente | Funciona nativamente |
| **GPU para modelos locales** | Si (directo) | Si (nvidia-container-toolkit) | Si (nvidia-container-toolkit) |
| **Debugging** | Facil (breakpoints directos) | Medio (attach al container, o run fuera) | Medio |

**Decision:** Opcion (C) Docker Compose + cloud para LLM API, con modo hibrido de desarrollo.

**Justificacion:**
1. Docker es **requisito obligatorio** para sandboxing (ADR-004) y para Qdrant (ADR-002). No hay opcion "sin Docker".
2. Claude API es **requisito obligatorio** para 5 de 6 agentes (ADR-001). No hay opcion "sin cloud".
3. Docker Compose unifica todos los servicios en un solo `docker compose up`.
4. El modo hibrido permite correr la app FastAPI fuera de Docker (para debugging con breakpoints) mientras los servicios (Qdrant, Ollama, PostgreSQL) corren en Docker.

## ADR-007: Modelo de ejecucion del sandbox y salida a red (R3 / D4)

**Estado:** Proposed (pendiente de revision de chief-architect)
**Fecha:** 2026-11-09
**Sustituye parcialmente a:** ADR-004 (red del sandbox, limites por defecto, montajes, perfil de seguridad, donde corre el motor).

**Contexto:**
La auditoria sobre `6135401` encontro que ADR-004 prometia red interna, rootfs de solo lectura y `tmpfs noexec` sin implementarlos: el sandbox con red usaba el bridge por defecto (alcanzaba gateway del host y servicios de metadatos), el cliente HTTP generado seguia redirecciones y re-resolvia el nombre (DNS rebinding), el workspace era escribible, la salida seguia symlinks sin tope y `cpu_count` no limita CPU en Linux. Ademas, si Docker fallaba, la API arrancaba con herramientas que no funcionaban ni avisaban.

**Hecho medido (Docker 29.9.3, daemon real):** una red `--internal` **no** impide llegar al gateway del bridge: un servicio del host escuchando en `0.0.0.0` fue alcanzado desde un contenedor de esa red. Con `-o com.docker.network.bridge.inhibit_ipv4=true` el bridge no tiene direccion en el host y el gateway, IMDS y otras redes dejan de ser alcanzables. Una red dedicada no equivale a una allow-list: la allow-list efectiva la da la topologia descrita abajo.

**Decision D4 — alternativas evaluadas:**

| | (A) API en contenedor con acceso al daemon (socket montado o proxy de socket) | (B) API en el host con Docker; Compose sin `docker.sock` |
|---|---|---|
| Superficie | Acceso al socket ~ root del host desde el contenedor de la API | El daemon solo es accesible para el proceso del host |
| Sandbox en Compose | Activo | Desactivado con error explicito |
| Complejidad | Media (socket-proxy, permisos) | Baja |
| Herramientas ofensivas | Disponibles en Compose | Solo en despliegues host+Docker |

**Decision: (B).** La API corre en el host con Docker; el Compose de produccion arranca con `SANDBOX_MODE=disabled`, sin `docker.sock`, y toda herramienta que ejecuta en sandbox (incluidas las ofensivas de Mike) responde `{"status": "disabled", "error_code": "sandbox_disabled", ...}`: un error explicito, nunca un stub ni datos inventados.

**Modelo de ejecucion y red (por ejecucion, efimero, sin daemon propio ni socket en contenedores):**

1. **Sin red por defecto:** `network_mode="none"`.
2. **Con red (solo herramientas ofensivas):** el objetivo se valida una vez (`EgressPolicy`): http(s), sin credenciales, todas las direcciones resueltas globales (se rechazan privadas, loopback, link-local/IMDS, CGNAT, gateway, multicast, NAT64/6to4/Teredo, IPv4 mapeada). Se **fija una IP**. Se crea una red `internal` + `inhibit_ipv4` y un contenedor reenviador L4 puro (misma imagen, rootfs de solo lectura, `cap_drop ALL`, limites) conectado a esa red con **alias = hostname** y al bridge por defecto; solo reenvia a `IP:puerto` recibido por argv. El sandbox se conecta **unicamente** a la red interna. Consecuencias: el nombre resuelve al reenviador (TLS/SNI y verificacion de hostname intactos extremo a extremo), no hay ruta al host, gateway, IMDS, Qdrant ni otros contenedores aunque el codigo no coopere, y el sandbox nunca resuelve fuera (cierra rebinding). El hostname no es autoridad tras validar; la autoridad es la IP fijada.
3. **Redirecciones:** el cliente generado usa un opener sin `HTTPRedirectHandler` y sin proxies de entorno (3xx = error). Defensa estructural: aunque un cliente las siguiera, no hay ruta a ningun otro destino.
4. **Rechazos explicitos:** objetivos con IP literal (no expresables como alias) fallan antes de crear recursos.

**Controles de ADR-004 realmente implementados:** rootfs `read_only`; `/tmp` tmpfs `rw,noexec,nosuid,nodev,size=64m`; entradas en bind **solo lectura**; unico escribible `/workspace/output` (bind), leido con `lstat`/`O_NOFOLLOW`, sin symlinks ni ficheros especiales, con tope por fichero (4 MiB), total (8 MiB) y numero (64); `ulimit fsize/nofile/core`; `cap_drop ALL`, `no-new-privileges`, `init`; memoria sin swap, CPU por `nano_cpus`, `pids_limit`; semaforo global de concurrencia; contenedor con el uid del proceso anfitrion; limpieza en `finally` solo de recursos propios (sandbox, reenviador, red, tmpdir).

**Diferencias con ADR-004 (deliberadas):**

| Aspecto | ADR-004 | ADR-007 |
|---|---|---|
| Defaults | 4 GB, 2 CPU, 600 s | 2 GB, 2 CPU, 300 s, 128 pids, 2 concurrentes (configurables por `SANDBOX_*`) |
| Perfil seccomp | Perfil personalizado (lista blanca) | **Perfil por defecto de Docker**; no se envia perfil propio (no probado exhaustivamente; riesgo documentado) |
| Red con acceso | `internal` + proxy por dominio (`boe.es`, ...) | `internal` sin IP de host + reenviador a una IP validada; sin allow-list por dominio |
| tmpfs | `/tmp` 2 GB | `/tmp` 64 MB |
| GPU | Soportada | No soportada en este modelo |
| Donde corre el motor | No especificado | Host con Docker (D4-B) |

**Consecuencias y limites:**
- Si Docker o la imagen faltan con `SANDBOX_MODE=docker`: staging/production **no arrancan**; development arranca con errores explicitos (`sandbox_unavailable`).
- El reenviador es el unico salto con ruta de salida; un reenviador comprometido solo puede dialar la IP fijada. Su codigo es de este repositorio y recibe el destino por argv.
- Un objetivo con varias IPs usa una; si es solo IPv6 el puente IPv4 del reenviador no podra alcanzarlo.
- Un objetivo HTTP puede observar el trafico en claro (propiedad de HTTP, no del reenviador).
- Verificacion de la topologia hecha con Docker Desktop 29.9.3; el job de CI con Docker real (ubuntu-latest) es la evidencia complementaria para Linux nativo. `inhibit_ipv4` y `internal` son opciones documentadas del driver bridge.
- El kernel se comparte (sin gVisor); sigue valiendo la mejora futura de ADR-004.
- Un escritor malicioso puede llenar disco hasta el tope de `fsize` por fichero dentro del tiempo limite; el tope total solo se aplica al leer.

**Rollback:** (1) inmediato, sin despliegue: `SANDBOX_MODE=disabled` apaga todas las herramientas con sandbox con error explicito; (2) revertir el commit de ADR-007 restaura el comportamiento anterior, que **no** es seguro (red bridge) y solo debe usarse con herramientas ofensivas apagadas; (3) las alternativas A/B se reevaluan si aparece un requisito de sandbox dentro de Compose.

**Pruebas:** unitarias (politica, topologia solicitada al SDK con mocks etiquetados, arranque fail-closed, tope de salida con sistema de ficheros real) y bateria con Docker real (F3.5, `pytest -m docker`, `FRAUDAI_DOCKER_TESTS=1`): sin red por defecto, gateway/IMDS/host/Qdrant inalcanzables, rootfs inmutable, `pids_limit`, symlink bloqueado, redireccion a IP privada bloqueada.
